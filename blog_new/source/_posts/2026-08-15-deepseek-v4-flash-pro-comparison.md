# 同一个任务丢给 DeepSeek 两款新模型：贵 3 倍的 V4-Pro 值不值？

DeepSeek 开源 Harness（dsh）有几天了，最近我做了个小实验：把同一个写作任务，分别丢给它家最新的两个模型——deepseek-v4-flash 和 deepseek-v4-pro 来分别看下实际效果和花销。

任务很简单：写一篇介绍 dsh 的技术博客。两个模型拿到了同样的条件——同样的任务描述、同样的背景材料（包括"我之前拆过 Claude Code 源码"这个作者视角）、同样的发布要求。

![DeepSeek V4-Flash 与 V4-Pro 对比：3 倍价差](/images/deepseek-v4-flash-pro-comparison/cover-1888x800.png)

两个模型各交了一篇 3000 字上下的稿子。拿到手我发现差距确实还蛮大。这篇文章把**两篇原稿完整贴出来**，自己对照着看；然后对着官方定价算一笔账：贵 3 倍的 V4-Pro，到底值不值～～

## 原稿一：V4-Flash 交的稿子

> **【原稿全文】DeepSeek 开源 Harness（dsh）：模型负责思考，"壳"负责干活**
>
> > 摘要：2026 年 8 月，DeepSeek 开源了第一款 Agent 产品 DeepSeek Harness（dsh）——"Model + Harness = Agent"的运行框架，核心口号是 Everything is a Plugin（一切皆插件）。这篇聊聊 dsh 是什么、为什么 Agent 需要一层 Harness、"一切皆插件"到底意味着什么，以及开发者预览版这个身份提醒我们什么。
>
> 8 月中旬，DeepSeek 开源了自己的第一款 Agent 产品：DeepSeek Harness，简称 dsh。v0.1，MIT 协议，发布当天 GitHub 就冲了好几万 star。
>
> 整个项目最显眼的一句话是 Everything is a Plugin——一切皆插件。
>
> 我看了官方发布页，翻了仓库结构，也读了不少社区讨论。这篇不写安装教程，只讲四件事：dsh 是什么、为什么 Agent 需要一层 Harness、"一切皆插件"到底意味着什么，以及开发者预览版这个身份提醒我们什么。
>
> **模型是马，Harness 是挽具**
>
> Harness 这个词原意是马具、挽具，引申义是"把马套上车的那套装置"。
>
> 用在 Agent 上很贴切：模型是那匹马，Harness 是把马的力气真正转化成"干活"的整套装置。
>
> dsh 的官方定位可以用一句话概括：**Model + Harness = Agent**。模型负责推理和生成，Harness 负责模型之外的一切——agent loop、工具调度、上下文管理、会话状态、权限链路。它提供的形态包括：Python 库和 dsh CLI、浏览器里的 Web UI、无界面的 headless 模式，以及 MCP 服务，底层跑在一个叫 Cordis 的插件内核上。
>
> 一句话：dsh 不是又一个"聊天窗口"，而是让你在上面搭建、运行、甚至改装 Agent 的运行时。
>
> **为什么 Harness 对 Agent 很重要**
>
> 先说一个容易被忽略的事实：**模型权重里不包含"干活"的能力**。
>
> 一个能真正完成任务的 Agent，至少需要五件事：感知（读文件、查状态）、决策（拆任务、定计划）、行动（调工具、执行命令）、记忆（记住上下文和中间结果）、恢复（出错后读日志、换路径、重试）。这五件事没有一件长在模型参数里，全靠外面的那层壳实现。
>
> 这层壳就是 Harness。它承载 agent loop，编排工具调用，管理上下文预算，维护多步任务的状态。这也是 DeepSeek 强调 Model + Harness = Agent 的原因——模型负责推理，Harness 负责把推理变成行动。
>
> 顺着这个思路往下想，会发现一个更重要的判断：**当头部模型能力越来越接近，Agent 的差距正在从"模型"转移到"壳"上**。谁的运行时更稳、上下文治理更聪明、工具调度更可靠，谁的 Agent 就更好用。我拆 Claude Code 源码的时候就有这个体感——真正影响好不好用的，往往不是模型多强，而是 runtime、会话管理、工具调度这些工程细节。dsh 是模型厂商第一次把这一层当作核心产品来认真做。
>
> **"一切皆插件"不是口号，是架构**
>
> dsh 最核心的设计理念，就是 Everything is a Plugin。
>
> 这不是营销话术，而是架构事实：在 dsh 里，几乎每个组成部分都是插件——
>
> - **模型是插件**：模型提供商可以插拔，今天用 DeepSeek，明天可以换别的
> - **工具是插件**：文件读写、代码执行、搜索，都以插件形式注册
> - **上下文和记忆是插件**：上下文怎么管理、记忆怎么存，可以换成自己的实现
> - **连 agent loop 本身都是插件**：循环不是写死在内核里的，可以被替换、被改写
>
> 内核只保留最小的一层"壳"，负责加载插件、按事件把插件串起来，其余全部交给插件。这个设计有三层意义：
>
> **可替换。** 想换模型、加工具，不用动框架本身，换插件就行。
>
> **可组合。** 功能以插件为粒度组装，像搭乐高，也像 Android 的应用生态——官方提供基础件，剩下交给社区。社区里已经冒出了插件市场、Web 端插件管理器这些周边项目，说明这个思路正在被验证。
>
> **可自修改。** 既然一切皆插件，Agent 理论上可以在运行时管理自己的插件——加插件、换插件、改自己的行为。很多报道把它称为"自进化软件"的雏形。听起来有点科幻，但"Agent 能改装自己"确实是这个架构最自然的结果。
>
> 对普通开发者来说，这意味着扩展 dsh 的成本，从"改框架"降到了"写插件"。
>
> **Web UI 和 headless，两种打开方式**
>
> dsh 提供了两种典型的使用形态，对应两类场景。
>
> **Web UI：人机协作的工作台。** 安装后拉起 Web UI，在浏览器里和 Agent 对话、查看会话、管理插件。适合你坐在电脑前，和 Agent 一起调试代码、边看边改的场景。官方仓库里提供了独立的 Web 应用包（npm 上的 `@deepseek-ai/dsh-web-app`），可以本地自托管；社区也有人做了 Electron 桌面壳，想当普通 App 用可以关注。
>
> **headless：无人值守的自动化。** 不需要界面，通过 CLI 或 Python SDK 以程序化方式驱动 agent 循环，适合写脚本、接 CI、跑批量任务，或者把 dsh 嵌进自己的产品里当"干活引擎"。官方部署指南里也给了两条接入路径：一条是 npx 一键拉起 Web 端，另一条是直接用 Python SDK 做完整接入。
>
> 两种形态共用同一套插件体系，切换成本很低。建议先开 Web UI 把交互玩明白，再把重复性任务脚本化、挪到 headless 里去跑。
>
> **别忘了：它还是开发者预览版**
>
> 最后说点冷静的。dsh 目前的身份是 **v0.1 开发者预览版（developer preview）**——虽然已经 MIT 开源，代码可读可改，但官方定位很明确：还不是稳定版。
>
> 这意味着几件事：
>
> - **迭代会很快**：功能、接口都在快速演进
> - **兼容性可能变化**：API、插件接口、配置格式都可能调整，甚至出现破坏性变更，不保证向后兼容
> - **别在关键生产链路上深度绑定**：拿它学习架构、写插件、跑实验完全没问题，但生产环境建议锁好版本、关注 changelog、给插件做版本管理
>
> 这类项目资料更新极快，本文基于 2026 年 8 月中旬的公开信息写成，具体以官方仓库和发布页为准。
>
> **结尾**
>
> dsh 的发布，在我看来是一个信号：模型厂商终于开始认真做"模型外面那层壳"了，而且选了最开放的方式——MIT 开源 + 一切皆插件。
>
> 无论 dsh 最终能不能成为主流，**"Agent 的差异在 Harness，而 Harness 应该是可拼装的"**这个判断，很可能会成为接下来一两年 agent 开发的共识。
>
> 如果你也感兴趣，建议做三件事：去官方发布页读一遍介绍，去 GitHub 仓库翻翻架构，然后动手写自己的第一个插件——毕竟一切皆插件，动手才是最快的理解方式。
>

## 原稿二：V4-Pro 交的稿子

> **【原稿全文】DeepSeek Harness：把 Agent 的工程质量，做成一堆可插拔的插件**
>
> DeepSeek 最近开源了一个 Agent 运行时，命令行名字叫 `dsh`，全称 DeepSeek Harness。它的 README 第一句就把姿态摆得很清楚：一个开源的 Agent harness，「一切皆插件」（Everything is a Plugin），底层跑在一个叫 [Cordis](https://github.com/cordiverse/cordis) 的框架上。
>
> 我最感兴趣的不是「DeepSeek 又发了个 Agent 产品」，而是它把一个平时被藏起来的层——运行时——摊开给你看。
>
> 这篇文章不讲教程，只把三件事讲清楚：Harness 到底是什么、为什么它对 Agent 如此重要、「Everything is a Plugin」到底意味着什么，然后顺带把 Web UI 和 headless 两种用法过一遍。最后要单独提醒一句：它仍是开发者预览版，兼容性随时可能变。
>
> **从「神话」回到「工程」，Agent 也一样**
>
> 我之前拆 Claude Code 源码时写过一句判断：真正决定 Agent 体感的，往往不是模型本身，而是 prompt 背后的 runtime、session 管理、tool 调度、compact 策略和 permissions 链路——那是 Agent 的「工程质量」，不是模型能力的「展示层」。
>
> DeepSeek Harness 干的正是这件事：把这一层工程质量，做成了一个开源的、可插拔的运行时。想先把它是什么讲清楚，绕不开一个很多人的疑问——harness 到底夹在哪一层？
>
> **Harness 是什么：模型外面那层壳**
>
> 先给个定义。Agent 不等于模型。模型只负责「给定上下文，吐出下一个 token」；但一个能真正干活的 Agent，还需要很多模型之外的东西：这一轮上下文怎么攒、工具怎么调度、读写文件要不要审批、session 怎么存怎么恢复、长任务怎么拆、子 agent 怎么派、后台任务怎么收。把这堆东西管起来的那一层，就是 harness。中文有人叫「座舱」，有人叫「运行时」，我觉得「运行时」最贴切。
>
> `dsh` 就是这样一个运行时。它做的事，是把上面这些能力组织成一棵「配置树」：你启动的每一个 dsh，都是启动时按顺序把插件一层层叠加起来的。
>
> 这里有两个贯穿全文的概念，先放出来：
>
> - **profile**：一个命名好的组合，存在 Harness 的 home 目录里。它声明自己叠加哪些 bundle、装了哪些树外插件，还保存一份你自己的 `cordis.patch.yml`。`web` 和 `headless` 是官方随包附带的两个模板 profile。
> - **bundle**：Cordis 配置行 + 它要挂载的代码的一种分发格式。`dsh-base` 是每个 profile 的第一层，装的是模型适配器、工具、持久化、沙箱、审批策略、凭据、遥测这些最基础的东西；`dsh-web-app` 在它上面加浏览器界面；`dsh-headless` 加的则是一个「跑完就退出」的一次性运行器。
>
> 为什么要这样组织？这就带出第二个问题。
>
> **为什么 Harness 对 Agent 重要：决定体验的是工程质量**
>
> 模型趋同之后，Agent 的差距会往后推一层，推到「运行时怎么定义行为」上。这是我之前反复讲的判断，放到 dsh 身上刚好对得上。
>
> 一个 coding agent 改文件之前，是先解释计划还是直接动手？遇到不确定的需求，是先问人还是先做个可回滚的草稿？这些「产品判断」不会从模型里自然长出来，它们被写进 prompt、tool 定义、权限策略和调度循环里——也就是 harness 里。
>
> dsh 把 Agent 的运转拆得很细。一次 **step** 是「一次模型请求 + 它调用的工具」；一次 **turn** 是零到多个 step。它的 session 日志是一条只追加的事件流，模型看到的上下文必须能从这条日志重建——用官方的话说，「model-visible means logged」（模型可见即已记录）。tool 的调用也不是裸奔，中间要过一条 `tools/pre-execute → tools/execute → tools/post-execute` 的管道。权限和审批同样是运行时的一部分：在 Web UI 里，凡是需要审批的操作，Agent 会先停下来问你。
>
> 这些不是「更聪明」，是「更可控」。对想把 Agent 真正塞进工作流的人来说，可控才是门槛。
>
> **Everything is a Plugin：没有特权核心**
>
> dsh 最特别的地方在它的架构主张：不只是工具是插件，而是**包括模型适配器、工具注册表、session 日志，甚至 agent 循环本身在内，每一个部件都是插件**。架构文档里写得很直白：没有需要打补丁的「特权核心」（no privileged core to patch），你想扩展它，就是把自己的插件挂到别人旁边。
>
> 支撑这套东西的是 Cordis。它是一个插件框架，插件向共享上下文贡献三样东西：服务（service）、带类型的事件（typed event）、可逆的副作用（reversible effect）。「可逆」很关键——插件卸载时，它注册的东西会自动收回，不留一堆孤儿状态。
>
> 落到工程上，最有意思的是 **seam**（能力接缝）这个设计。一个 seam 是一个可替换的能力，分三个角色：定义接口的 Service Definition、实现它的 Service Provider、使用它的 Consumer。因为文件系统和子进程共享同一个执行世界，把 provider 指到一个远程沙箱，Bash、PTY、LSP 会跟着一起搬过去，不需要给每个能力单独打补丁。
>
> 说人话就是：你想换模型、换工具、换沙箱、换 UI，都是换一个插件的事，而不是改内核。对一个开源的 Agent 运行时来说，这个设计直接决定了它将来能被社区改造成什么样。
>
> **怎么用：Web UI**
>
> 最省事的入口是 Web UI，一条命令：
>
> ```sh
> npx @deepseek-ai/dsh web
> ```
>
> 它会启动一个浏览器界面，默认地址是 `http://127.0.0.1:3080`。第一次进去按官方引导做三件事：
>
> 1. **配模型**：Settings → Models，填一个 DeepSeek API key 并保存。配好即时生效，不用重启服务。
> 2. **选工作区**：Choose workspace，把启动 `dsh` 时所在的目录加进来并选中。没选工作区之前，会话输入框是不可用的。
> 3. **跑任务**：直接发一句类似 `Summarize this repository` 的话。Agent 能读写工作区文件、跑命令、派子 agent、维护计划；需要审批的操作，UI 会先弹出来问你。
>
> 如果从源码跑，就是 `git clone`、`pnpm install`、`pnpm run build`，然后 `pnpm dsh web` 那套。
>
> **怎么用：headless**
>
> 不想开浏览器、只想丢一个任务进去拿到最终答案就走，用 headless：
>
> ```sh
> dsh --profile headless "run the tests"
> ```
>
> 它做的事很克制：起一个全新的持久化 session，把任务当作一条普通用户消息丢进去，等 agent 安静下来，把最后一条非空回复打到 stdout，然后退出。整个过程**不开任何监听端口**。任务正常收尾退出码是 0，出错是 1，错误信息走 stderr。
>
> 限制也很清楚，官方文档明说了：**一次只接一个任务**，没有交互式追问；你给一段任务文本，它跑完就回来。
>
> **先泼一盆冷水：还是开发者预览版**
>
> 这一点我觉得必须单独说，因为现在外面有些文章把它讲得像一个已经稳定的产品。
>
> 官方 README 的原话是：DeepSeek Harness 目前处于 **developer preview（开发者预览）**，迭代很快，「**会有破坏兼容性的改动**」（THERE WILL BE COMPATIBILITY-BREAKING CHANGES）。npm 上的版本号是 `0.1.0-rc.6`——rc 是 release candidate，不是 stable。
>
> 这意味着几件事：API 和配置格式可能变，你现在写的插件、记的 patch，过两个版本未必还能原样跑；文档里也标了不少 Known Limitations（比如 headless 单任务、patch 是整行替换而非深合并）。所以它现在更适合**尝鲜、读源码、理解架构**，而不是拿来做生产依赖。真要在自己项目里用，建议盯紧 GitHub 仓库的更新，别把行为写死。
>
> **我的判断**
>
> 如果「AI 的下半场不拼神话、拼系统工程」这个判断成立，那 harness 会是下一阶段竞争里越来越重要的一块。模型公司自己做 harness，逻辑和它自己做 coding 产品是一样的：入口层如果只靠包装模型能力，迟早被模型层吃掉；把运行时做成开源、可插拔的底座，反而是在往「工程质量」和生态那条更难抄的路上走。

## 四回合，各赢一半

两篇全文都在上面，我自己对比下的感受是：

| 回合 | 谁赢 | 一句话理由 |
| --- | --- | --- |
| 谁真读过文档 | Pro | 命令、端口、版本号、seam 三角色，细节全能对到官方文档；Flash 更像读了报道之后写的综述 |
| 谁更敢编 | Pro | Flash 的"几万 star"查无出处；Pro 最冒险的表述是把官方警告原样大写引用 |
| 谁更好读 | Flash | "马与挽具"一段顶 Pro 一整节；Pro 判断准但门槛高 |
| 谁适合直接发 | Flash | front matter 完整、延伸阅读给的是站内链接，说明它理解了"这是发在我博客上的文章" |

一句话来总结下两个版本的优点：**Flash 是合格的科普作者，Pro 是靠谱的技术编辑。** 最好的做法是让 Pro 写主体，把 Flash 的开头嫁接过去。

这是一次写作任务的单点实测，样本量是一，替代不了 benchmark。但"便宜的模型更敢编"这个现象，这次又应验了——用 Flash 的产出，事实核查这一步省不掉。

## 价格：Pro 全面是 Flash 的 3 倍

效果说完了，说钱。下面是 DeepSeek 官方定价页的数据，单位是元/百万 tokens：

| 模型 | 时段 | 输入（缓存命中） | 输入（缓存未命中） | 输出 |
| --- | --- | --- | --- | --- |
| v4-flash | 空闲 | 0.05 | 1.5 | 4.5 |
| v4-flash | 高峰 | 0.10 | 3.0 | 9.0 |

最直观的一条：**Pro 对 Flash 是全维度 3 倍价**——缓存、输入、输出都是整整 3 倍，没有哪一项手下留情。

时间上更要留神的一条：**这套价格 2026 年 8 月 17 日 0 点才生效。** DeepSeek 刚切换到峰谷分时定价：高峰时段（北京时间 9:00–12:00、14:00–18:00）全价，其余时段半价。此次调价相对旧价涨幅明显。如果你走的是第三方托管（OpenRouter、DeepInfra 等），报价和官网差异不小，下单前自己再对一遍。

## 算一笔账：一篇文章，最贵四毛一

价格表看着抽象，直接换算成"写一篇文章要花多少钱"。

按一次典型写作估算：给模型喂 3 万 tokens 的参考资料（按缓存未命中算），它输出 5 千 tokens 的成稿：

| 时段 | V4-Flash | V4-Pro |
| --- | --- | --- |
| 空闲 | 0.07 元 | 0.20 元 |
| 高峰 | 0.14 元 | 0.41 元 |

（估算口径：纯 API 调用，不含平台加价；实际有缓存命中会更便宜。）

也就是说：**用最贵的组合（Pro + 高峰），一篇 3000 字技术文的成本是四毛一；最便宜的组合（Flash + 空闲）只要七分钱。** 写作场景下，Pro 贵是贵，但绝对值小到不值得为它纠结——一次返工的 token 都比这个差价多。

真正拉开差距的是 agent 场景。在 dsh 里跑一个中等复杂度的任务，agent loop 几十轮循环，每轮都重发上下文——按累计输入 50 万 tokens（其中 40 万缓存命中）、输出 5 万估算：

| 时段 | V4-Flash | V4-Pro |
| --- | --- | --- |
| 空闲 | 0.40 元 | 1.19 元 |
| 高峰 | 0.79 元 | 2.37 元 |

单任务差 3 倍。一天跑 20 个任务，一个月下来两个模型的差距接近 500 块；批量跑评测、跑数据清洗的团队，这个差距直接乘上去。

这里有两个现成的省钱杠杆。最狠的一个是缓存：agent loop 每轮都重发前文，缓存命中率极高，"把稳定的系统提示词和参考资料放在输入最前面"这种缓存友好编排，比选哪个模型更影响账单。另一个是峰谷：批处理任务本来就适合挂半夜，直接半价——和"半夜跑 CI"的运维习惯正好是同一件事。

## 所以，怎么选

四条实战建议：

1. **事实敏感的内容用 Pro。** 要引用版本号、命令、价格的技术长文，Pro 那种"连 rc 后缀都要解释一句"的劲儿正是你要的。用它仍然要抽查，但它编造的概率肉眼可见地低。
2. **初稿和社交内容用 Flash。** 比喻能力不输，速度快，价格三分之一。发之前记得人工过一遍数字和专名。
3. **批量任务用 Flash + 空闲时段。** 两个折扣叠加，单任务成本能压到 Pro 高峰价的六分之一。
4. **让便宜的写、让贵的审。** Flash 出初稿、Pro 做事实核查和结构打磨——这个组合比单押任何一个模型的效果都好。

至于 dsh 本身——它还是 0.1.0-rc.6 的开发者预览版，官方把丑话写在了 README 顶部：会有破坏兼容性的改动。拿它学架构、写插件没问题，生产环境再等等。
